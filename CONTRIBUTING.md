# Contributing to Pulseq repositories

Thank you for your interest in contributing to the Pulseq ecosystem.

Pulseq welcomes contributions from MRI physicists, engineers, software developers, clinicians, researchers, educators, students, and users of Pulseq-compatible tools.

## How to contribute

Useful contributions include:

- bug reports
- feature requests
- documentation improvements
- examples and tutorials
- tests and validation datasets
- interoperability reports
- code improvements
- release and packaging improvements
- workshop and community-led development ideas

## Before opening a pull request

Before starting substantial work, please open an issue or discussion to describe the proposed change.

This is especially important for:

- API-breaking changes
- Pulseq file format or specification changes
- MATLAB/Python interoperability changes
- large refactors
- new dependencies
- release or packaging changes
- changes to safety-related functionality
- changes affecting multiple repositories or implementations

## Pull request expectations

Pull requests should be small, focused, and reviewable whenever possible.

A good pull request includes:

- a clear explanation of the problem and solution
- related issue or discussion links
- tests or validation steps
- documentation updates when behavior changes
- backward-compatibility notes
- examples if user-facing behavior changes

Large pull requests may be difficult to review. Maintainers may ask that large changes be split into smaller stages.

## Interoperability

Because Pulseq is a cross-implementation ecosystem, contributors should consider whether their change affects:

- MATLAB Pulseq
- PyPulseq
- Pulseq file format compatibility
- sequence examples
- validation tools
- documentation
- downstream scanners, converters, or interpreters

If the change affects interoperability, please describe the expected behavior and any compatibility risks.

## FAIR software practices

Contributions should support software that is:

- **Findable** through clear names, metadata, releases, and documentation
- **Accessible** through open repositories, documented installation, and clear licenses
- **Interoperable** through standards, examples, validation, and cross-language compatibility
- **Reusable** through tests, documentation, versioning, citation information, and clear APIs

## Community expectations

Please participate constructively and respectfully. Technical critique is welcome; personal criticism is not.

All contributors are expected to follow the Pulseq Code of Conduct.
